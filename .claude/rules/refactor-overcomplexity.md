# プロジェクト統合リファクタリング指示書

## 目的
プロジェクト全体を俯瞰し、外部仕様（ユーザーから見た振る舞い）を一切変えずに、内部アーキテクチャ・依存関係・コードベースを大規模かつ安全に整理・最適化する。

## エージェントの基本原則（厳守）
1. **段階的実行の原則**
   一括で全てのファイルを書き換えないこと。必ず「計画立案」と「フェーズごとの実行」に分け、各フェーズの完了時に動作の整合性を担保すること。
2. **要件維持の原則**
   機能の追加・削除・仕様変更は絶対に行わない。
3. **対話型進行**
   大規模な破壊的変更（ディレクトリ構造の大幅な変更など）を行う前は、必ず計画を提示し、人間の承認（GOサイン）を得てから実行すること。

## 大規模リファクタリングの観点（マクロ視点）
以下の観点でプロジェクト全体を評価し、改善案を出すこと。
- **アーキテクチャと境界の整理**
  - レイヤー間（UI、ビジネスロジック、データアクセス等）の責務分離は適切か？
  - 循環参照（Circular Dependency）が発生していないか？
- **共通化と凝集度の最適化**
  - 複数ファイルに散らばる同一のドメインロジック・型定義・ユーティリティを単一ソースに集約できるか？
  - 逆に、不必要な共通化によって結合度が高まっている部分（密結合）を分離できるか？
- **ディレクトリ構造の最適化**
  - 機能別、またはドメイン別にファイルが直感的に配置されているか？

## 実行フェーズ（以下の手順に従って進行せよ）

### Phase 1: 現状分析と課題抽出
- プロジェクト全体を走査し、上記の「マクロ視点」および「過剰な複雑さ（不要な抽象化や動的計算）」の観点から課題をリストアップする。
- 課題ごとに「なぜ問題か」「どう解決するか」を簡潔に出力する。
- **※この段階ではコードの変更を行わない。**

### Phase 2: リファクタリング実行計画の作成
- Phase 1の課題を解決するための具体的な「ステップバイステップの実行計画」を作成する。
- 計画は以下の構成で出力すること。
  1. ステップ番号と概要
  2. 対象ファイル（移動・変更・新規作成）
  3. 期待される効果
- **※計画を出力したら一旦停止し、「この計画で実行を進めてよいか？」と人間に確認を求めること。**

### Phase 3: 段階的実行（人間の承認後）
- 承認を得たら、Phase 2の計画を「ステップ1つずつ」実行する。
- 1つのステップが終わるごとに、インポートエラーや型エラーが発生していないか確認し、問題があれば自己修復する。
- 完了したら「ステップX完了」と報告し、次のステップへ進む。

### Phase 4: 最終検証と報告
- 全ステップ完了後、不要になったファイル（デッドコード）の削除漏れがないか確認する。
- 全体を通して変更したファイルのサマリーと、残された技術的負債（もしあれば）を報告する。
